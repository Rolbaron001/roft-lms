## 4. Storage, backups and the value chain

Moved behind the learning side by Roland on 26 September: see Order of work,

### 4.1 Backup retention
**Status:** done, 21 September. **Needs:** confirming to Heidi.

The disk reached 93 per cent. The cause was not the application data, which is
a little over 1 GB. It was 8.5 GB of backups, of which everything older than
seven days accounted for 0.08 GB.

Two fixes went in on 21 September:

* The pre deploy backup now takes the database only. The evidence archive, a
  full copy of every uploaded file at roughly 1 GB, is taken nightly instead of
  before every deploy.
* Evidence archives are kept by count, the newest three, rather than by age.
  Age released nothing because all the weight was recent.

A third fix followed the same day. Docker images were also kept by age at 72
hours, and six deploys in one day all sat inside that window, so the prune
reclaimed nothing while 4.6 GB accumulated. Images are now kept by count, the
newest two versions, as app and tools pairs.

Result: 93 per cent full down to 60 per cent, 7.5 GB free.

Heidi's own summary of the underlying problem is correct and worth keeping:
the evidence archive is the cost, not the database dump, and both halves are
required or a restored Portfolio of Evidence points at files that no longer
exist.

**24 September: Docker image retention had never worked.** The line that chose
which versions to keep listed each image's date and commit but not its name, so
the filter looking for `roft-lms` matched nothing. Under `set -euo pipefail` an
empty match stopped the deploy script on the spot, after the deploy had
finished and before it tidied up or logged "Deployed". Every deploy since
21 September left its images behind: 16 images and 6.5 GB by this morning, with
the disk at 84 per cent. Fixed in `scripts/auto-deploy.sh`; the nine stale
images were removed by hand, taking the disk to 68 per cent.

Evidence backup retention was checked at the same time and **is** working: it
keeps three and removes one each night.

**Decision:** Roland, 21 September afternoon. **Status:** built, awaiting

The platform must fit clients who are not Curiosa: not all in South Africa,
and not all seeking accreditation. A corporate client may want a course for

organisation it is.

determine how the users view them." Independent switches allowed platforms that

**Two questions, each with one answer.**

*What sits at the top:*

| Choice | What it means |
|---|---|
| Qualification / Programme | One thing. A learner is put onto the qualification and that is what they work through. Curiosa's shape. |
| Qualification and Programme, separately | Two different things. |
| Programmes only | No accreditation record. |
| Neither | Everything stands on its own. |

*What a learner works through:*

| Choice | What it means |
|---|---|
| Courses | The course is the thing. |
| Study units | The study unit replaces the course. Requires a qualification above it, and is unselectable without one. |

*Two switches that stand on their own:* statutory reporting, workplace
experience.

Three consequences follow from the choices rather than being set twice: the

## 9. Reading Word documents correctly

**Found by:** Roland, 21 September. **Status:** fixed, awaiting deploy.

"I think the problem is that you are not reading strikethrough text
correctly." Struck through text was being read as live text.

This is not only a job sheet problem. The same reader runs over every Word
document a provider uploads: the curriculum it transcribes assessment criteria
from, the alignment document it builds study units from, and the workbooks and
answer guides Capture turns into questions a learner answers.

### 10.1 Separate development and production sites
**Decided.** **Owner:** Roland, delegated to Claude. **Status:** done and
running, 25 September. Roland's three decisions and what was built are recorded
at the end of this item.

Linda strongly disagreed with changes going straight to the live server. The
concrete cost is already on record: on 19 September an alignment upload landed
three seconds before a deploy restarted the application, and the modules did not
link. The agreed answer is a second container on the same server acting as a
development site, rather than a second server.

It fits the pipeline that already exists. Images are built by GitHub Actions and
never on the server. Production pins a commit; development can follow the newest
build. A change is pushed, lands on development automatically, is tried there,
and **the same image** is then promoted to production. Nothing is rebuilt
between testing it and releasing it.

**What it has to be, whatever else is decided:**

* **Its own database.** Not a second copy of the application pointed at the live
  one. A development build pushes its schema when it deploys; against the live
  database that would change production's structure from the test site, and
  stress-test data would land among real learners' records.
* **Its own file storage,** for the same reason.
* **Its own address,** so nobody can mistake one for the other.

**Three decisions for Roland:**

1. **The address.** `lms.roftbusiness.org` already points at this server and
   already has a certificate; it served the sandbox tenant parked on
   22 September. Using it for development costs nothing and needs no DNS change.
   The alternative is a new name such as `dev.lms.curiosa.academy`.
2. **What development starts with.** Empty; a copy of live with learner details
   removed; or live copied as it is. A copy is far more useful for testing, and
   is also a second place holding learner records, which POPIA cares about.
3. **Memory.** See 10.6. At idle the second site fits. Under a ten-user stress
   test on the same machine it may not, and the site that would suffer is live.

**Roland decided, 24 September:**

1. **Address: `lms.roftbusiness.org`.** It replaces the parked sandbox tenant.
2. **Data: a straight copy of live.** Today live holds staff and programme
   material but no real learners, so the copy carries little personal
   information. That stops being true with the first real cohort: from then on,
   every refresh copies real learner records to development, and development
   has to be protected and retained like live.
3. **Memory: ask Linda for 2 GB** in the 1 TB quote. The development site is
   built now; the ten-user stress test waits for the upgrade.

**Running since 25 September, 08:56.** `https://lms.roftbusiness.org` is the
development site; `https://lms.curiosa.academy` is live and was healthy
throughout. Checked, not assumed:

| | |
|---|---|
| Data copied | All 107 tables match live row for row, except sign-ins (72 on live, 0 on development, cleared on purpose) |
| Files copied | 1.0 GB |
| Mail | Set on live, absent on development |
| Caps | Development capped at 384 MB and 0.4 of a processor; live uncapped |
| Banner | On every development page including sign-in; none on live |
| Schedule | Five existing jobs kept; the daily 16:00 release replaced |

**Faults found on the way, each fixed before it did harm:** the scripts were
committed without the executable bit, so the server could not have run them;
the address check compared against live's name, which this server maps to
127.0.1.1, and so refused a correct address; and the image tidy kept a stale
`latest` image that left development 20 MB short of room for its next update.

**Disk is the binding limit.** A development update needs 5500 MB free before
it pulls, which keeps 3 GB for live whatever the download turns out to be. The
first automatic update, at 07:15 on 25 September, pulled 743 MB rather than the
2.3 GB budgeted, because the images share most of their layers, and left
4777 MB free. Each later update first removes development's own previous
version, which brings it back to about 5520: a margin of 20 MB. Any growth in
backups, logs or testers' uploads, and development stops updating, with the log
saying why. Live is protected either way. This is the concrete case for the
1 TB and 2 GB quote in 4.2 and 10.6.

How it works: `DEPLOY.md`, "A development site beside live".

### 10.2 Release window
**Decided by Roland, 24 September: Friday night.** Linda's recommendation. Live
updates on Friday nights, so an update never lands during the working week.

This replaces the daily 16:00 release, and it only works once 10.1 exists.
Without a development site, a weekly release means Heidi sees nothing new for a
week. With one, she sees a change on development the day it is made, and live
takes it on Friday. What live takes on Friday is **the image development is
running**, not the newest commit: the release is the thing that was tried.

**In place since 25 September:** cron runs the promotion at 22:00 each Friday.
It refuses an unhealthy development site, and a version development has run
for under six hours, so a Friday-evening push waits a week rather than going
out untried. For a release that cannot wait, on Roland's say-so:
`cd ~/roft-lms && ./scripts/promote-to-production.sh --now`.

**A weakness to fix, found 25 September.** The six-hour rule looks only at the
version development is running at 22:00. A push late on a Friday therefore
holds back the whole week, including versions development had already run for
days. The better rule is to promote the newest version development ran for six
hours, which the development deploy log already records with times. Left until
after the first Friday release, because changing the release process on the day
it first runs would be its own late push. **Until then: no pushes after about
15:45 on a Friday.**

### 10.3 Stress testing with simulated learners

Five to ten testers work through the qualification on placeholder text. Linda
wants ten concurrent users reading and writing to the database.

**This should run on development, not on live.** Five to ten people filling a

**What the platform needs before testing can start:**

* **Accounts for the testers.** Nothing to build, found 25 September: People

  enrolment form), so they stay in the WhatsApp group. **Create the testers on

* **A way to hand over sign-in details.** The development site sends no mail at

### 10.4 Off-site backup on a separate cloud
**Decided with the 1 TB tier.** Linda recommended backing up to a different
provider, such as Amazon, so that one provider's outage cannot take the server
and its backups together. Priced by whether the data is kept ready or archived.

Already supported: `scripts/backup.sh` sends backups to an S3 bucket when
`BACKUP_BUCKET` is set, and today it is empty. This is configuration and a
credential, not a build. **Needs:** the bucket and its access key, from whoever
holds the account.

**A block found and fixed, 25 September.** The backup runs in the tools
container, which sat on a network with no route out, so it could never have
reached a bucket. It was noted on 16 September as "cannot resolve DNS,
harmless today", and was the item the note to Linda says "we are fixing". It
was worse than that: the hourly job that sends queued notifications runs there
too, and was proved unable to resolve or reach the mail server, so the first
notification ever queued would have failed. The tools container now has the
application's two networks; the database keeps its no-route-out network alone.
Goes to live in the Friday release of 25 September.

### 10.5 Full and incremental backups
**Linda's recommendation, not decided.** A full backup monthly, with daily
incrementals that carry only what changed. Today each night takes a full copy of
every evidence file, about 1.3 GB each, and keeps three.

Worth doing, and bigger than it sounds. An incremental is only restorable with
the full backup it depends on, so retention stops being "keep the newest three"
and becomes "keep every chain intact". Best done after 10.4, since off-site
storage changes where those chains live.
