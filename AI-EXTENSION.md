# The AI extension — how it is built, and how to build it again

Written 20 September 2026, because Roland intends to put the same thing into
the **NBTC Management Dashboard**
(`F:\CHRISTO-CLAUDE\Projects\BMA\Apps\National Border Targeting Centre Management App\`)
once it is proven here.

This is the design and the reasoning, not a tour of the code. It is written to
be read from another project by somebody who cannot see this one.

---

## What it is for

One capability: **work a structure out of documents that do not describe
themselves.** In the LMS that means reading a QCTO curriculum PDF and producing
modules, topics, elements and assessment criteria. Everything else the platform
does — filing a document by its name, reading a folder that carries its own
`blueprint.json` — is rules, and rules need no model.

That distinction is the first design decision and the most useful one. **Keep
the model on the smallest possible surface.** Where a rule can do the job, a
rule does the job: it is free, instant, and cannot invent an assessment
criterion that somebody is later judged against.

## The shape

Four files, and the claim that "a second provider is a file rather than a
project" has now been tested three times and held.

```
lib/extensions/base.ts        the contract. imports nothing.
lib/extensions/index.ts       the registry, the credential store, the one call
lib/extensions/claude-code.ts a CLI on the same machine
lib/extensions/gemini.ts      an HTTP call
lib/extensions/openai.ts      an HTTP call
```

`base.ts` imports nothing at all, so its types can be used from a browser form
without dragging a database driver into the bundle. That is a Next.js-specific
trap and worth repeating in any framework: keep the shapes a form needs in a
file that reaches nothing.

### The contract

```ts
type AiProvider = {
  name: string;              // stored against the person. never change one.
  label: string;
  description: string;
  defaultModel: string;      // a starting point with a shelf life, not a promise
  writesFiles: boolean;      // can it answer into a file, or only in its reply?
  credentialFormat: {
    word: string;            // "token" or "API key" — the screen says this
    shape: RegExp;           // what it can *know* is wrong, not what is valid
    source: string;          // "run `claude setup-token`…" / "sign in at…"
    looksLike?: string;      // only where the issuer keeps a stable prefix
  };
  listModels?(token): Promise<string[]>;   // ask, do not hardcode
  availability(tenantId?): Availability;   // can it run *here*, right now
  run(input): Promise<ExtensionResult>;    // prompt in, text out
};
```

Everything above the contract — what to ask, how to read the answer, what may
be written — lives in the caller. The provider only knows how to be asked.

### The four hard-won fields

Each of these exists because its absence caused a specific failure. They are
the parts worth copying rather than reinventing.

**`writesFiles`.** Claude Code is an agent with file tools: given a working
directory it reads the documents as files and writes the answer as a file, and
it does that far more reliably than it returns JSON in prose. Gemini and OpenAI
are one request and one answer. The caller must not know which it is talking
to, so it names the file it wants (`answerFile: "proposal.json"`) and the
**registry** appends the right sentence — "write your answer to X" or "reply
with that JSON object and nothing else". Before this, the prompt said "the file
is the answer", which handed to Gemini is an instruction to return nothing.

**`credentialFormat.shape`.** A shape check can only honestly answer *"is this
another provider's credential?"* — never *"is this valid?"*. Only the provider
knows that, and it says so clearly on the first call. Pinning a prefix or a
version number fails **closed on a valid credential**, which is the worst
direction: the person is holding the right thing and being told they are wrong.
Google has issued Gemini keys beginning `AIza` and beginning `AQ.`; Gemini's
rule therefore names no prefix and only excludes `sk-` (Anthropic's and
OpenAI's). Claude's keeps `sk-ant-` because it is generated by a documented
command, and additionally rejects `sk-ant-api…` by name — an Anthropic **API
key** is a different product from a Claude Code **token**, and somebody holding
one needs to be told which they have, not to check their typing.

**`availability(tenantId)`.** Answers "can this run *here*", asked at read time
rather than remembered, because the answer changes without the platform
changing — somebody signs in, a container is rebuilt, a desktop app moves its
executable. The settings screen marks a provider that cannot run on this
deployment, and does not default to one.

**`listModels`.** A `defaultModel` is a guess with a shelf life. Google retired
`gemini-2.5-flash` for new users and said so in the middle of a test. Bumping
the name only resets the clock, so a provider that can be asked *is* asked, and
the person picks from what their own credential reaches today. A test fails if
a model name appears anywhere except the provider's own file.

## The credential

The one credential this platform stores, and it took a decision to do it.

- **Per person, never per tenant.** Each member of staff pastes their own. An
  administrator setting theirs up does not set anybody else's up.
- **Sealed at rest** (AES-256-GCM, key from `AI_TOKEN_KEY` or derived from
  `AUTH_SECRET`), never returned to a browser, never written to a log, never
  held on a provider object — a provider carrying a credential would be a
  provider serving whoever configured it.
- **Three states, never collapsed**: the deployment *offers* extensions; the
  person has one *available*; this sitting has it *on*. Only the third licenses
  a run, and it is false at the start of every sitting and forced false at sign
  out.
- Supplied to `run()` **per call**. The registry reads it at the moment of a
  run and does not return it.

A test pins all four properties and is treated the way the tenant-isolation
test is treated.

## What the caller does

```ts
const result = await runExtension(session, {
  task: "ingest_qualification",   // recorded, for the history
  prompt: INSTRUCTION,            // what to find. says nothing about format.
  workdir,                        // documents staged as files
  answerFile: "proposal.json",    // where, *if* this provider can write one
  timeoutMs: 900_000,
});
```

The registry checks registered → available → on → credential readable →
provider available, and returns a sentence somebody can act on for each
failure. It records every run — provider, model, task, prompt **hash**,
duration, outcome — never the prompt itself and never the credential.

## Rules that earned their place

**Nothing is written until a person has seen it.** Every run produces a
*proposal*, reviewed on a screen and committed in one act. A model produces
something plausible from a document that says nothing of the kind, and the only
defence is a human reading it against the source. The review screen states
where the plan came from — a blueprint, a model, or filing rules — because
"what looked at my documents" is a question a provider can be asked.

**Refuse rather than truncate, at both ends.** If the documents exceed what can
be sent, refuse: a plan built from half a curriculum looks exactly like a plan
built from all of it. The *output* side needs the same guard — an answer that
stopped because it ran out of room came back as success until this was fixed,
and whether that was caught depended on where the cut happened to land.

**Say what the failure was in words somebody can act on.** Not the provider's
raw error. A revoked token, a rate limit, a wrong model, a key of the wrong
kind, a job too large — each gets its own sentence and its own next step. Strip
the credential out of any message before showing it: some providers echo the
key back in their own errors.

**A model is the smallest part of the feature.** Most of the value here is in
the parsing, the classification rules, the guards and the review screen. The
model does one thing that rules cannot.

## Building it elsewhere

For the NBTC dashboard, the parts that transfer are, in order:

1. `base.ts` — the contract, essentially unchanged. It is the valuable bit.
2. The credential store and the three states.
3. The registry's per-provider prompt shaping (`writesFiles` / `answerFile`).
4. The review-before-commit pattern, and the provenance line on it.
5. The failure messages, which are mostly transferable prose.

What will differ is the task: NBTC will want something other than a curriculum
out of its documents. Keep the same discipline — rules where rules suffice, the
model on the smallest surface, nothing written unread.

**Before writing any of it, check the environment rather than recalling it.**
Whether a CLI is installed, what a key looks like, which models exist: look, do
not remember. Every one of the four fields above exists because that was not
done once.
